> 森林瀑布 · 2026年8月
> 扒完 Palantir 官网和文档之后，越往下看，越觉得它不是"大数据平台"——而是一套从数据到行动的完整闭环。

把 Palantir 官网一页页扒下来，再把产品文档、架构和实际能力逐条对照之后，我越来越觉得：

**Palantir 把太多原本分散的东西，做成了一套完整闭环。**

而且，越往下扒，越能看到两个容易被忽略的发现。

---

## 一、Palantir 的核心，不是某个产品，而是一个闭环

很多人第一次接触 Palantir，会把它理解成"大数据平台""数据分析平台"，或者"知识图谱平台"。

都不太准确。

如果把今天 Palantir 的能力拆开来看，至少可以看到几个相互咬合的部分：

**Foundry** 负责数据基础设施和 Ontology；
**HyperAuto** 负责把 ERP、CRM、SAP 等业务系统的数据快速接入、转换，并进一步生成可用的 Ontology；
**AIP** 把大模型、Agent、Ontology、业务逻辑和工具调用连接起来；
**Gotham** 承载具体的任务和业务应用；
**Apollo** 则负责把这些能力部署到不同基础设施、不同网络和不同运行环境中。

其中最容易被看走眼的，是 AIP。

它不是"又一个聊天机器人"。

Palantir 现在甚至已经把 **Ontology MCP** 单独做成了一套能力：Object Type、Action Type、Query Function 都可以被暴露为 MCP 工具，让外部 Agent 直接读取本体数据、查询业务对象，甚至通过预定义 Action 执行业务动作。

这件事真正重要的地方在于：

**大模型不再只是"回答问题"，而是开始够得着企业真实世界。**

模型调用的不是一个孤零零的 API，而是企业已经定义好的对象、关系、业务动作和约束。

查对象、改状态、创建任务、触发流程……

这些动作背后，都有 Ontology 作为业务语义和系统事实的承载层。

所以，把这些能力放在一起看，Palantir 真正形成的是：

> **数据 → 语义 → 规则 → 动作 → 反馈**

这才是它最难拆掉的东西。

做一个反事实推演。

如果把 Ontology 整个拿掉，会发生什么？

数据管道当然还能跑，Apollo 当然还能部署，应用也可以继续存在。

但问题是：

**业务对象失去了统一语义，Action 失去了明确的业务对象和状态载体，Agent 也失去了一个稳定的企业事实层。**

于是系统很容易重新退化成：

> 数据平台 + AI 应用 + 一堆业务接口。

技术组件依然存在，但真正的业务闭环断掉了。

所以，"没有 Ontology 也能做"这句话，从基础设施角度当然成立；但从 Palantir 的价值结构来看，就不成立了。

---

## 二、最值得研究的地方：它把"业务动作"放进了语义层

这是我认为 Palantir 最值得国内企业软件研究的一点。

传统企业软件的链路通常是：

> 数据 → 报表 → 人看结果 → 人做判断 → 人操作系统

系统负责"看清楚"。

决策和行动，仍然在系统之外。

而 Palantir 在尝试做另外一件事情：

> 数据 → Ontology → 业务逻辑 → Action → 系统执行

也就是说：

**业务动作本身，成为了系统的一部分。**

Palantir 的 Action Type 可以定义参数、逻辑以及对 Ontology 的编辑；相关规则也可以修改 Ontology 中的对象，或者通过 Webhook 等机制触发外部系统行为。

再往前一步，Agent 通过工具调用这些 Action。

于是大模型不再只是：

> "建议你把库存降下来。"

而可以进一步变成：

> "发现库存异常 → 查询相关对象 → 判断是否满足业务条件 → 调用预定义 Action → 修改业务状态或触发后续流程。"

这中间当然仍然需要权限、审批、人工确认等治理机制，尤其是高风险业务。

但架构发生了一个很重要的变化：

**"该做什么"不再全部存在于人的脑子里，而开始被编码进系统的语义、规则和动作中。**

这就是从"分析型系统"走向"操作型系统"。

Ontology 在这里也就不再只是一个漂亮的数据模型。

它真正承担的是：

**把企业世界中的对象、关系、状态、规则和动作，变成机器可以理解、调用和执行的结构。**

这里还有一个我觉得特别有意思的变化。

过去，大多数 ToB 软件最终都是**给人看的**。

报表给人看，BI 给人看，知识库给人看，智能问答也给人看。

所以很多 AI 项目最后变成了：

> Harness / Agent / Skills / MCP
> ↓
> 智能问答 / 问数 / 知识库 / RAG
> ↓
> **人**

然后再由人决定下一步怎么办。

甚至有时候，为了证明 AI 有价值，还得反过来绞尽脑汁想：

**"我们到底应该给 AI 找一个什么应用场景？"**

Palantir 的思路恰恰相反。

它试图把链路变成：

> **业务数据 → Ontology → 业务逻辑 → 推理 / 决策 → Action → 业务系统**

这里最关键的变化，不是"有没有 Agent"。

而是：

**数据的终点不再只是人，而是业务本身。**

一个系统是"为人提供信息"，另一个系统则开始"参与业务运行"。

这可能是 Palantir 最值得研究的地方。

---

## 三、一个被高估，一个被低估

顺着这个逻辑往下推，会得到一个有点反直觉的结论：

**非结构化数据建模容易被高估，结构化数据的本体建模反而容易被低估。**

今天谈大模型，大家第一反应往往是：

PDF、邮件、会议记录、语音、图片……

似乎 AI 最大的价值，就是把这些非结构化数据"变成知识"。

当然，这非常重要。

但除此之外，Palantir 的产品演进还指出了另一条值得注意的路线：

**把企业已经存在的大量结构化业务系统，快速变成本体和可执行业务语义。**

HyperAuto 就是一个非常典型的例子。

Palantir 官方目前将 HyperAuto V2 定义为围绕 Data Sync、Builder Pipeline 和 Ontology 的自动化能力，可以利用源系统元数据自动推断数据同步、转换逻辑，并生成对应的 Ontology；目前 V2 主要支持 SAP，而此前的 V1 则覆盖过 Salesforce、Oracle NetSuite 等业务系统。

为什么这件事重要？

因为结构化数据有一个巨大的优势：

**它是确定的。**

ERP 里面有订单、库存、供应商、物料；

CRM 里面有客户、商机、合同；

MES 里面有设备、工单、产线。

这些东西本来就有明确的字段、主键、关系和业务约束。

所以，与其花巨大力气让大模型"理解一个表格"，不如直接把这些确定的数据结构映射成企业 Ontology。

这条路线的 ROI 往往非常直接。

因为最终撬动的不是"知识问答"，而是：

**库存、资金、订单、产能、供应链、排产、客户、合同……**

这些才是真正和企业经营结果直接相连的东西。

非结构化数据同样重要，只是它通常需要多走几步：

> **非结构化数据 → 信息抽取 → 结构化事实 → Ontology → 业务动作**

而结构化业务数据可以更直接地进入：

> **业务系统 → Ontology → 业务动作**

所以真正值得警惕的不是"大模型做非结构化建模没有价值"。

而是：

**如果只盯着非结构化数据，就可能低估了 Ontology 对整个结构化业务世界的价值。**

## 四、Palantir 最难复制的，可能不是技术，而是"全面"

再回到文章开头那句话：

**Palantir 太全面了。**

这不是一句吐槽，反而可能是它最大的护城河之一。

Palantir 有一个非常有代表性的角色：FDE，Forward Deployed Engineer，前出部署工程师。

这个角色的特殊之处在于，它不是传统意义上的"开发工程师"。

你需要同时理解：

数据工程、业务流程、Ontology、应用开发、AI、部署运维……

然后把这些东西真正塞进一个客户的业务现场。

现在 Palantir 甚至已经推出 AI FDE，让 Agent 直接操作 Foundry，执行数据转换、代码仓库管理、Ontology 构建和维护等任务。

这反而进一步说明了一件事情：

**Palantir 真正构建的不是一个单点工具，而是一套完整的企业数字世界。**

数据进来以后怎么办？

怎么理解？

怎么形成业务对象？

对象之间是什么关系？

什么状态意味着什么？

什么条件下应该采取行动？

行动之后如何回写？

Agent 如何调用？

权限怎么控制？

最终如何部署？

这一整套东西，它都在做。

这也是为什么我认为，国内企业软件如果只是简单复制某一个 Palantir 产品，很难真正复制它的价值。

因为真正难复制的不是某个算法。

而是：

> **从数据到语义，从语义到行动，再从行动回到业务数据的完整闭环。**

---

## 五、这也解释了中国 ToB 真正值得补的，不只是技术

如果把今天很多企业的数据系统画出来，大概率还是这样：

> 数据 → ETL → 数仓 → BI → 看板 → 人决策

这套体系没有错。

过去二十年，它解决了大量企业的数据问题。

但它的终点仍然是：

**人。**

系统把信息整理好，告诉人发生了什么。

然后人做判断。

然后人去另一个系统里操作。

而 Palantir 更进一步尝试的是：

> **数据 → 语义 → 决策逻辑 → Action → 执行 → 反馈**

两者最大的差异，不是用了没用 AI。

甚至也不是有没有知识图谱。

而是：

**系统到底停在"帮助人决策"，还是开始具备"参与业务行动"的能力。**

所以我越来越觉得，企业 AI 下一阶段真正值得研究的，不只是 RAG、Agent 或大模型本身。

而是：

**AI 到底连接到了什么。**

如果 AI 连接的只是一个搜索框，它还是聊天机器人。

如果 AI 连接的是企业 Ontology、业务规则、Action 和真实业务系统，它才真正开始进入企业的"操作层"。

Palantir 现在正在做的，恰恰就是后者。

---

## 写在最后

扒完 Palantir 官网和文档之后，我最大的感受反而不是：

**"Palantir 太强了。"**

而是：

**"Palantir 太完整了。"**

它真正厉害的地方，不是拥有 Foundry、AIP、Gotham、Apollo、HyperAuto 这么多产品。

而是这些产品最终都在回答同一个问题：

> **如何让企业的数据，最终变成可以理解、可以决策、可以行动的业务系统？**

所以，Palantir 的"全"既是护城河，也可能是它的天花板。

因为对绝大多数企业来说，没有必要复制一个完整的 Palantir。

更现实的路径，反而是切它最有价值的一块：

> **结构化业务数据 → Ontology → 业务规则 → Action → Agent → 执行闭环**

把这一块做深、做透、做轻。

这可能才是国内企业软件真正有机会的地方。

当 LLM 不够用时，真正稀缺的从来不只是一个更会聊天的模型。

而是：

**有没有一个足够可靠的语义层，能够把大模型的"认知"接到企业真实世界的"行动"上。**

这可能才是 Palantir 最值得我们研究的地方。
