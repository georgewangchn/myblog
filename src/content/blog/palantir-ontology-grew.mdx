> 森林瀑布 · 2026年8月
> 很多人以为 Palantir 的本体是设计出来的，其实它是长出来的——从数据工程的土壤里，一点一点长出来的。

![Palantir 本体生长示意图](/assets/cover/palantir-ontology-grew.png)

很多人说起 Palantir 的 Ontology（本体），语气像在聊一个高深的设计范式：

一群架构师坐在白板前，把企业世界里的对象、关系和规则想清楚，然后把它设计成一个漂亮的本体。

但我越扒 Palantir 的官网、产品文档和架构，越觉得事情没这么"聪明"。

> **Palantir 的本体，不是先设计出来，再把数据塞进去的。**

它更像是从一个非常朴素的底座上，一点一点长出来的。

而这个底座，恰恰就是很多人不太关注的数据工程。

---

## 一、Foundry 的底座，本来就是湖仓

Palantir 商业化过程中，Foundry 是非常关键的一层。

而 Foundry 往下看，本质上还是一套数据平台：把企业里散落的数据接进来、存起来、加工、转换，再让上面的应用使用。

听起来一点都不性感。

但我反而觉得，这恰恰是关键。

因为企业真正需要长期接入、长期治理、长期加工的数据，大头从来不是 PDF、会议录音这些东西。

而是 ERP、CRM、SAP、MES、供应链系统……

这些系统每天都在产生结构化数据。

订单、库存、客户、供应商、物料、合同、工单、设备……

**Ontology 后面真正站着的，就是这些东西。**

所以很多人研究 Palantir，直接从 Ontology 开始看，很容易漏掉一个问题：

**这么多业务对象，Palantir 凭什么能把它们建出来？**

答案可能没有那么玄学。

因为它前面已经有一层长期运行的数据工程。

---

## 二、时间一长，共性就出来了

湖仓的数据开发层，一边跑业务，一边积累数据。

而这些数据，很多来自 ERP、CRM、SAP 这类高度结构化的业务系统。

这里有一个非常有意思的地方：

**这些系统看起来千差万别，但真正描述的业务世界，并没有那么大的差别。**

换一家公司。

订单还是订单。

客户还是客户。

供应商还是供应商。

库存还是库存。

物料还是物料。

换一个行业，字段名可能变，表结构可能变，业务流程可能变。

但"对象—关系—状态—约束"这套骨架，往往还在。

制造业可能是：

> 订单 → 物料 → 供应商 → 生产

零售可能是：

> 订单 → 商品 → 库存 → 客户

航空可能是：

> 航班 → 飞机 → 航线 → 乘客

看起来完全不是一个行业。

但从数据工程往下挖，你会发现，它们其实都在描述一个现实世界。

**共性，就是本体能够长出来的土壤。**

---

## 三、为什么偏偏是"共性"？

因为本体真正贵的地方，从来不是画出来。

画一个 Object Type 不难。

难的是：

**每来一个客户，你都要重新画一遍。**

A 公司做一套。

B 公司完全不一样，再做一套。

C 公司又不一样，再做一套。

那本体就很难成为产品。

它只能是项目。

> **做一个，废一个。**
> **再做一个，再废一个。**

这也是为什么很多企业的知识图谱、本体项目，最后都会变成一个很重的定制工程：

专家来了。

开会。

梳理业务。

画模型。

对字段。

做映射。

写规则。

验收。

项目结束。

下一家公司重新开始。

问题不是本体没价值。

而是**每一次建模都没有形成下一次建模的生产资料。**

Palantir 恰恰拥有另外一套条件。

大量结构化业务系统。

长期的数据开发。

持续的 Schema 映射。

大量重复出现的业务对象。

再把这些东西不断沉淀成平台能力。

于是事情开始发生变化。

第一次接 SAP：

> 这是一个订单表。

第二次接 SAP：

> 这个订单结构好像见过。

接得多了：

> 订单就是 Order，客户就是 Customer，物料就是 Material。

再往后：

> 这几张表之间的关系，大概率就是这些。

再往后：

> 这些东西可以自动映射。

**本体就是这么一点一点"长"出来的。**

---

## 四、所以本体真正依赖的，不只是模型，而是积累

这也是我觉得 Palantir 很值得研究的地方。

很多人把 Ontology 理解成一个建模问题。

其实它首先是一个**积累问题**。

你没有足够的数据，没关系。

你有数据，但没有长期的数据工程，也不行。

你有数据工程，但每家公司都完全不一样，也不行。

真正关键的是：

> **大量结构化业务系统 + 高度重复的业务对象 + 长期的数据工程积累 + 持续的平台化。**

这些东西叠起来，本体才开始从"专家手里的模型"，变成"平台里的能力"。

HyperAuto 很有意思，就是因为它把这件事情进一步自动化了。

过去是工程师看源系统：

> 这个字段是什么？
> 这张表是什么？
> 这几个表怎么关联？

后来变成系统帮你推：

> 这个字段可能对应什么？
> 这张表可能对应什么对象？
> 这些关系可能怎么建立？

再进一步：

> **系统直接帮你把数据映射成 Ontology。**

这时候，本体就已经不是一个纯人工设计产物了。

它背后实际上积累的是：

**大量过去做过的数据工程。**

---

## 五、反过来推：没有这层积累，本体很难长大

做个反事实推演。

假设没有长期的数据工程。

会怎样？

每接一个系统，都重新理解 Schema。

每个客户，都重新确认字段。

每一个对象，都重新判断它从哪里来。

每一条关系，都重新验证。

每一个规则，都重新写。

本体就会越来越依赖少数专家。

专家不在，项目就停。

项目一多，专家又不够。

最后变成典型的 ToB 定制项目：

> **人越多，项目越多；项目越多，维护越重。**

再假设企业之间完全没有共性。

那就更麻烦。

A 企业的订单是 A 的订单。

B 企业的订单是 B 的订单。

C 企业又是一套完全不同的东西。

上一家做出来的东西，下一家完全用不上。

那本体就很难产生规模效应。

所以我反而觉得：

**Ontology 的核心门槛，不只是"有没有本体专家"，而是有没有足够长的工程积累，让一次项目经验能够变成下一次项目的生产资料。**

这可能才是 Palantir 真正难复制的地方。

---

## 六、本体长出来以后，事情才真正有意思

前面说的是"怎么长出来"。

但长出来以后，它带来的变化更重要。

传统湖仓的链路通常是：

> 数据 → 加工 → 分析 → 报表 → 人

数据算完了。

人看。

人判断。

人再去业务系统操作。

本体出现之后，业务对象、关系、状态、规则开始有了统一的语义承载。

于是：

> **数据 → Ontology → 规则 → Action → 业务执行**

这条链就接起来了。

这时候，Ontology 就不再只是"描述企业是什么"。

它开始描述：

**企业现在是什么状态，以及企业可以做什么。**

订单是什么。

库存是什么。

客户是什么。

这些是静态语义。

但订单能不能取消？

库存能不能调整？

任务能不能分派？

设备能不能停机？

这些已经不是"数据"。

而是**动作**。

Palantir 的 Action 把这一层接了起来。

于是本体从"描述世界"，开始变成"驱动世界"。

这才是我觉得最有意思的地方。

---

## 七、而 Agent，只是后来接进来的那只手

这时候再看大模型和 Agent，位置就很清楚了。

很多 AI 项目的链路是：

> Harness / Agent / Skills / MCP
> ↓
> RAG / 知识库 / 问数 / 智能问答
> ↓
> **人**

最后还是人看。

人判断。

人操作。

Agent 解决的是"怎么更方便地把信息交给人"。

而 Palantir 这条路线更像是：

> **业务数据 → Ontology → 规则 / 推理 → Action → 业务系统**

Agent 接进来以后，只是把"谁来触发 Action"进一步智能化。

所以真正关键的并不是：

**有没有 Agent。**

而是：

**Agent 后面有没有一个已经长出来的业务世界。**

没有 Ontology，Agent 调的还是一堆零散 API。

有了 Ontology，Agent 调的是：

> Customer
> Order
> Inventory
> Shipment
> Maintenance Task
> ……

以及这些对象对应的业务动作。

这时候，Agent 才真正有"手"。

---

## 八、这也解释了为什么我不太认同"一上来就做本体"

现在回头看国内很多"对标 Palantir"的项目，我反而觉得顺序经常搞反了。

一上来：

画本体。

建知识图谱。

定义几百个 Object Type。

然后开始想：

**"这个本体到底能干什么？"**

甚至为了证明本体有价值，开始拼命找应用场景。

这其实挺累的。

因为本体不是一个孤立的知识工程项目。

**它需要土壤。**

数据从哪里来？

业务对象是不是稳定存在？

不同系统之间有没有共性？

Schema 映射能不能复用？

业务规则有没有长期积累？

Action 能不能真正回到业务系统？

这些东西没有，硬做一个本体出来，也很容易变成一棵盆景。

看起来很漂亮。

但不长。

真正值得先做的，可能反而是那些很"不性感"的东西：

**数据工程团队。**

**稳定的数据底座。**

**ERP / CRM / SAP / MES 等业务系统的持续接入。**

**长期积累 Schema 映射和业务语义。**

这些东西做好以后，本体反而没有那么玄学。

因为你已经积累了足够多的"现实世界"。

---

## 写在最后

所以我越来越觉得：

**本体不是设计出来的，是长出来的。**

当然，最后一定有人设计它。

一定有人定义 Object Type。

一定有人定义 Link。

一定有人定义 Action。

但这些设计不是凭空来的。

它们背后站着的是：

大量真实业务系统，

长期的数据工程，

反复出现的业务对象，

一次次客户项目，

以及这些项目不断被沉淀、复用、自动化的过程。

所以本体真正的生长路径，更像是：

> **业务系统 → 数据底座 → 数据工程 → 共性积累 → Ontology → 规则 / 推理 → Action → 业务执行 → 反馈**

> **不是先有一棵本体树，再往上面挂数据。**

而是先把土壤做厚。

数据越来越多。

业务对象越来越清晰。

共性越来越明显。

工程经验越来越多。

然后某一天你会发现：

**原来这些东西已经不是一堆表了。**

它们已经开始构成一个企业可以计算、可以推理、可以行动的世界。

这时候，本体就长出来了。

所以，如果今天有人问我：

**"做企业本体，第一步应该干什么？"**

我的答案可能不是：

> 先找一个本体专家。

而是：

> **先把数据和业务真正跑起来。**

> **本体不是一张白板上的设计图。**

**它是企业数字化长期积累之后，结出来的果子。**

而真正厉害的地方，是果子长出来以后，还能继续长出规则、Action、Agent，最后把决策重新送回业务本身。

这才是 Palantir 这条路线最值得研究的地方。
